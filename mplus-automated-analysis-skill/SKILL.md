# Mplus 通用分析工作流

## 核心原则

1. **用户可见内容中文优先。** 除 Mplus 必须读取的内部文件、变量名和语法外，目录名、报告名、表名、字段名、提示语尽量使用中文。
2. **AI 不自由生成标准模式的 Mplus 模型骨架。** LPA 必须从 `references/模型模板登记.yaml` 选择已登记模板；其他标准模块必须由 Runtime 的受控结构化编译器生成，且分析家族与验证状态以 `references/支持矩阵.md` 为准。遇到未覆盖的模型，进入“专家模式”，不得伪装成标准分析。
3. **能运行不代表规范。** 运行前校验“用户需求 → 分析设计清单 → 模板 → 最终 .inp”；运行后再校验“Mplus 实际识别的模型 → 输出 → 报告”。
4. **不静默修改研究数据。** 不自动删除异常值、不自动填补缺失、不自动做 Z 标准化。任何转换都记录在审计文件中。
5. **统计判断必须可追溯。** 模板、判断规则和报告中的关键结论都必须关联 `Source Registry`。
6. **重大问题优先。** 对抗性审查只检查会导致分析结论不可信的重大错误，不挑措辞和非必要增强项。
7. **原始数据只读。** 所有生成文件放入新的分析项目目录，禁止覆盖用户原始数据。

## 先路由，再建模

首先运行 `catalog`，并读取 `references/支持矩阵.md`。不得因为用户提到“潜在变量”就默认路由到 LPA。

检测到 Mplus 后，还必须读取 `references/Mplus版本适配.md` 和 `references/版本兼容.yaml`。对版本专属高级语法，只在版本满足条件且已有对应受控实现时使用；核心标准模型优先保持 7+ 通用语法。

- `standard`：Runtime 可从结构化分析设计生成受控代码。当前包括 EFA、CFA、SEM、观测/潜变量中介、基础线性增长、LCA 和完整 LPA。
- `guided`：Runtime 已登记官方来源，但关键约束和代码仍需研究者确认。核心路线包括测量不变性、多层潜变量模型、GMM/LCGA、LTA、RI-CLPM、ESEM 和复杂抽样。
- `expert`：贝叶斯潜变量模型、DSEM 及任意复合模型。Agent 可以组织流程、数据和结果审计，但禁止在没有完整设计时自动补全模型。

路径回归作为结构模型的基础能力保留。IRT、生存、缺失数据/多重插补和 Monte Carlo 不属于普通用户的首要入口，只在研究问题确实需要时通过 `catalog --all` 查看。不要为了显得“什么都支持”而推荐不适合 Mplus 的分析。

`standard` 表示代码生成路径已受控，不表示用户的特定模型在统计上自动成立。

## 执行流程

### 第 -1 步：先确认研究设计能回答什么

读取 `references/分析前检查.md`。优先从用户已有的研究方案、问卷、数据说明和对话中提取信息，只追问真正影响模型选择的缺口：研究问题、横截面/纵向/嵌套/分组结构、变量角色、测量时间、聚类与权重、缺失如何产生，以及结论属于描述、关联、预测还是因果。

这一步是轻量核对，不要求用户填复杂表格。数据已经收集完也可以继续分析，但必须在报告中说明无法补救的设计限制。观察数据不得仅因使用 SEM 就写成因果结论。

### 第 0 步：环境检测

运行 Runtime 的 `doctor`：

- 识别 Windows/macOS；
- 寻找 Mplus 可执行程序；
- 获取 Mplus 版本；
- 匹配版本适配配置，并在 `catalog --mplus <路径>` 中显示版本相关的功能边界；
- 在 macOS 识别 Mplus 程序是 arm64、x86_64 还是 universal2，并说明是否经 Rosetta 运行；
- 检查版本兼容表；
- 检查 Python 版本和数据读取依赖是否齐全；
- 检查项目路径写入权限。

默认先自动检查环境变量、系统 PATH、Windows 常见 Program Files 目录、macOS `/Applications/Mplus` 及用户 Applications。**不要一开始就询问零基础用户 Mplus 路径。**

- 只找到一个可运行且能识别版本的 Mplus：直接使用，向用户简短告知已找到的版本；
- 用户只知道安装文件夹：`--mplus` 可接受该目录，Runtime 自行寻找其中的 `Mplus/mplus(.exe)`；
- 自动检测失败：才请用户选择 Mplus 安装目录或可执行文件；
- 找到多个版本且可能影响兼容：列出版本供用户确认，不让用户手输路径。

如果最终仍找不到 Mplus，明确说明未运行。不要假装已经运行。

若 `doctor` 返回“环境待配置”，先告诉用户缺少什么及其用途，再询问是否允许配置本 Skill 的独立 Python 环境。**只有得到明确同意后**，在 macOS 运行 `./scripts/运行Mplus分析.sh bootstrap --yes`，在 Windows 运行 `.\scripts\运行Mplus分析.ps1 bootstrap --yes`。该命令会创建 `.mplusflow-venv`，并只在其中安装 `runtime/requirements.txt` 列出的依赖；没有 Python 时，会在可用的 Homebrew 或 winget 中安装 Python 3.12。不得在用户未同意时运行安装命令。

Mplus 是商业软件，Skill 不下载、安装或绕过其许可证。环境准备完成后仍找不到 Mplus 时，才请用户确认其合法安装位置。

当前产品优先验证 Mac M 系列。Windows 的路径发现、PowerShell 入口和静态兼容检查可以自动执行，但没有 Windows 真机时必须写“尚未实机验证”，不得写“Windows 已支持”。

首次安装或更换 Mplus/Runtime 版本后，默认先运行 `self-test --output <新目录>`。自检会生成与操作系统、架构、Mplus 版本和 Runtime 版本绑定的 `Mplus自检凭证.json`，正式分析默认使用该凭证。

如果自检因环境问题暂时不能完成，或用户明确希望先检查代码和数据，可说明边界后使用 `--provisional-environment` 进行一次“未自检试运行”。这不是静默降级：报告会写明结果不可直接作为正式研究结论，用户完成自检后必须复跑。未收敛、不可识别、变量/样本数错配、SAVEDATA 错配等重大问题不因试运行而放行。

自检凭证由 Agent 管理并自动传给 Runtime，不要要求零基础用户手动复制凭证路径。

### 第 1 步：识别分析家族与最少必要信息

优先从用户已有文件和对话中获取，不重复询问。一次只问一个最影响模型选择的问题，并给出简短推荐；正常情况下最多三轮。所有分析至少需要数据、变量角色、变量类型、缺失编码和研究目标。再按模块收集因子归属、路径方向、时间点、分组、聚类、类别范围或间接效应等必要设定。LPA 额外需要：

当用户只提供数据、没有研究问题时，先运行 `inspect-data`，生成数据画像和 2—3 个可考虑方向。不自动执行一组模型后替用户选择故事；只有用户明确要求“做功能测试”时，才可以在标注“仅供测试”的独立目录中并行尝试多种分析。

- 数据文件；
- 作为剖面指标的变量；
- ID 变量（如无则自动生成行号 ID）；
- 缺失值编码（可从数据识别后请求确认）；
- 类别范围（未说明时标准模块为 1—5 类）。

“是否标准化变量”不是默认动作。只有用户明确要求，或研究设计明确需要时才做，并写入分析设计清单。

### 第 2 步：数据审计与转换

Runtime 读取 `.sav/.xlsx/.xls/.csv/.dta/.txt/.dat` 等支持格式，不论分析家族都生成：

- `01_数据检查/数据质量检查报告.md`
- `01_数据检查/变量对应表.xlsx`
- `02_分析数据/Mplus分析数据.dat`
- `02_分析数据/分析设计清单.json`

内部 Mplus 变量统一改成 ASCII 且不超过 8 字符，例如 `V000001`，通过变量对应表映射回原变量名。Mplus 数据文件不写表头。

数据画像可标记重复行、高缺失变量和 IQR 异常记录，但不得自动删除。缺失比例不能单独判定 MCAR、MAR 或 MNAR；异常标记也不等于录入错误。只有能回查原始记录或用户明确授权的处理才可改变分析数据，并记录前后样本量。

样本量提示是软提醒，不是运行门槛。样本量低于规划参照时，如果用户仍要分析，应照常运行，并在数据检查与最终报告中同时写明当前样本量、建议的规划参照、模型特有风险和参考文献。不得用单一“样本量达标”替代功效分析，也不得为了得到方便的样本量反推效应量。

在进入 LPA 前必须检查：

- 指标变量是否存在；
- 指标是否为数值型连续变量；不超过 10 个唯一值时默认停止，只有研究者明确确认后才可按连续变量处理；
- 是否误把 ID、权重、分组变量纳入指标；
- 完全缺失、零方差、极低变异变量；
- 重复 ID；
- 样本数在转换前后是否一致；
- 缺失值是否按设计编码；
- 原始变量与 Mplus 内部变量的顺序是否一致。

### 第 3 步：生成受控模型

非 LPA 标准模块将研究设计写入 JSON，然后调用 `run-spec`。Agent 不得把自由文本直接插入 `MODEL:`；因子、回归、间接效应、时间分数和类别数必须通过结构化字段编译。具体字段见 `references/结构化分析设计.md`。

LPA 继续使用 `LPA-BASE-EV0` 和分阶段随机起始值流程：

采用分阶段随机起始值策略：

1. 初筛运行；
2. 检查最佳 loglikelihood 是否重复；
3. 未重复则自动增加随机起始值后重新运行；
4. 稳定后再进行 TECH11/TECH14 比较；
5. TECH14 出现局部最优或 bootstrap 不收敛警告时，不得把该 p 值当作有效证据。

具体策略见 `references/LPA分析规范.md` 和 `references/规则登记.yaml`。

### 第 4 步：运行后反校验

解析 `.out` 后必须验证：

- `THE MODEL ESTIMATION TERMINATED NORMALLY`；
- Mplus 实际使用的样本数；
- Mplus 实际识别的连续指标；
- 类别数；
- 估计量；
- 最佳 loglikelihood 是否重复；
- 是否存在 fatal error、局部最优、负方差/奇异信息矩阵等严重警告；
- AIC/BIC/SABIC、Entropy、类别比例、平均后验概率；
- TECH11/TECH14 是否成功且可解释。

如果“分析设计清单”与 Mplus 实际识别结果不一致，停止生成论文结论并报错。

### 第 5 步：模型比较与结论

不得用单个指标机械选类别数。

先排除未通过硬门槛的模型，再综合：

- BIC / SABIC / AIC；
- TECH11（如适用）；
- TECH14（如成功且无可信度警告）；
- Entropy；
- 平均后验分类概率；
- 类别规模；
- 参数估计稳定性；
- 类别是否具有实质解释。

Runtime 只生成“统计证据摘要”和“候选推荐”；最终文字解释必须明确哪些是统计证据，哪些是理论解释。证据冲突时写“证据不一致，需要结合理论解释”，禁止强行给出确定答案。

### 第 6 步：导出结果与教学材料

默认生成：

- `03_Mplus代码/1类别_分析代码.inp` … `5类别_分析代码.inp`
- `03_Mplus代码/代码逐段说明.md`
- `04_Mplus原始结果/*.out`
- `05_分析结果/类别模型比较表.xlsx`
- `05_分析结果/个体类别归属.xlsx`
- `06_分析报告/LPA分析报告.md`
- `07_参考依据/代码模板来源.md`
- `07_参考依据/模型判断依据.md`
- `07_参考依据/参考文献.md`

代码说明必须解释每个主要 section 的作用、为什么这样写、哪些部分来自认证模板、哪些部分根据用户数据填充。

### 第 7 步：强制质量审查

先运行程序化硬检查，再执行独立对抗性审查。

若当前 Agent 平台支持子 Agent / fork / task：调用 `agents/对抗性审查员.md`，只授予读取权限。若不支持，则主 Agent使用同一审查清单进行第二遍独立审查。

审查重点：

- 分析目标是否被替换；
- 变量是否错配；
- 样本是否意外变化；
- 模板是否被未经允许地改写；
- Mplus 报错/重大警告是否被忽略；
- 结果表是否与 `.out` 一致；
- 报告的模型选择理由是否与证据表一致。

没有重大问题时，不向普通用户展示审查报告；只在内部 manifest 记录 `审查状态=通过`。发现重大问题且无法自动修复时，生成 `08_质量审查/质量审查发现的问题.md`，并明确说明哪些结果暂不建议用于论文。

## 标准模式禁止事项

- 禁止根据“常见写法”凭空添加模型参数；
- 禁止因为 Mplus 正常结束就默认模型可靠；
- 禁止隐瞒 Mplus warning；
- 禁止把 Entropy 当类别数唯一标准；
- 禁止把任意 `p < .05` 当成必选更多类别的机械规则；
- 禁止把类别比例阈值伪装成公认硬标准；
- 禁止在用户未授权时自动 Z 标准化；
- 禁止覆盖原始数据；
- 禁止生成无法追溯来源的“权威标准”。

## 不得误报支持范围

安装包中的模块状态以 `catalog` 实时输出和 `references/支持矩阵.md` 为准。文档中出现某种分析名称，不等于它已完成自动化认证。
